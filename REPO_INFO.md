Setup / Run Instructions
------------------------
Prerequisites:
- .NET 10 SDK
- SQL Server or LocalDB (LocalDB used by default)

Steps:
1. Clone
   git clone https://github.com/jaydeepprajapati-official/RideMatchingSystem.git
   cd RideMatchingSystem

2. (Optional) Update connection string
   Edit RideMatching.Api/appsettings.json or set environment variable:
   ASPNETCORE_ConnectionStrings__DefaultConnection

3. Apply EF Core migrations & create DB
   dotnet tool install --global dotnet-ef
   dotnet ef database update --project RideMatching.Api --startup-project RideMatching.Api

4. Run API
   dotnet run --project RideMatching.Api
   - The app runs with HTTPS by default. Note the port shown in the console.

5. Run tests
   dotnet test

Postman (manual collection)
- Create a new collection and add requests below (use base URL https://localhost:{port}): E.g. https://localhost:7047/scalar/
  1) Create driver
	 POST /api/v1/drivers
	 Body (JSON): { "name": "Alice" }
  2) Go online
	 POST /api/v1/drivers/{driverId}/online
  3) Update location
	 PUT /api/v1/drivers/{driverId}/location
	 Body: { "latitude": 20.0, "longitude": 73.0 }
  4) Create ride
	 POST /api/v1/rides
	 Body: { "riderId": "rider-1", "pickupLatitude":20.0, "pickupLongitude":73.0, "destinationLatitude":20.1, "destinationLongitude":73.1 }
  5) Check ride
	 GET /api/v1/rides/{rideId}
  6) Driver accept/start/complete
	 POST /api/v1/drivers/{rideId}/accept  (Body { "driverId":"..." })
	 POST /api/v1/drivers/{rideId}/start
	 POST /api/v1/drivers/{rideId}/complete

- To capture SignalR events with Postman you can use the Postman WebSocket / SignalR support or a small Node/JS test client.

Short README
============
Architecture overview
---------------------
- Single API project (RideMatching.Api) containing controllers, EF Core DbContext, domain entities, a hosted BackgroundService (RideMatchingWorker), and a SignalR hub (RideHub).
- Flow: Rider creates a ride -> a MatchingJob is queued -> RideMatchingWorker claims the job, finds nearby available drivers (using DistanceCalculator), reserves a driver and assigns the ride -> notifications delivered via SignalR -> drivers update status through driver endpoints.
- Persistence: EF Core with SQL Server. Concurrency handled using atomic ExecuteUpdateAsync calls and database transactions.

Assumptions / Tradeoffs
----------------------
- Assumptions:
  - Drivers regularly update location; LastLocationAt freshness is used (30s cutoff) to consider candidates.
  - Single-process worker is acceptable for MVP; worker claims jobs with DB atomic updates to avoid duplicate processing.
  - SignalR group membership is not authenticated in the prototype.

- Tradeoffs:
  - Simplicity over scalability: matching runs inside API process (BackgroundService) rather than external matching service or message broker.
  - Spatial query implemented in-memory via Haversine; this is OK for small scale but not optimized for large driver sets.
  - DB-centric concurrency (ExecuteUpdateAsync) relies on SQL Server atomic updates; no distributed locking implemented.

Scalability considerations
-------------------------
- Short-term:
  - Offload matching to a separate service/process and use a message broker (RabbitMQ, Kafka, Azure Service Bus) for RideRequested events and assignment commands.
  - Add indexing and convert location to spatial/geography types; use spatial queries in DB for efficient radius searches.
  - Horizontally scale worker(s) with careful job claiming and visibility timeouts.

- Long-term:
  - Split into microservices: RiderService, DriverService, MatchingService. Use event-driven architecture (Pub/Sub) to decouple components.
  - Use a fast key-value store (Redis) for frequently-updated driver location data and proximity queries (geospatial indexes in Redis).
  - Introduce distributed tracing, metrics, and alerting (OpenTelemetry, Prometheus, Grafana).
